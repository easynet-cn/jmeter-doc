## 1. 场景概述

全链路压测是最接近真实生产环境的性能测试，需要从方案设计、脚本开发、环境准备、执行监控到结果分析的全流程规划。本章提供一套完整的全链路压测方法论。

**你将学到：**
- 压测方案设计（流量模型 → 脚本 → 执行 → 分析）
- 分布式压测完整配置
- 监控体系搭建（InfluxDB + Grafana）
- 压测执行 CheckList
- 结果分析报告模板
- 常见风险与应对

## 3. 阶段一：方案设计

### 3.1 目标定义

| 维度 | 内容 |
|------|------|
| **业务目标** | 验证系统能否支撑双11峰值流量（预估1000 QPS） |
| **技术目标** | 找到系统瓶颈、验证水平扩展能力、建立容量模型 |
| **SLA 目标** | P99 RT < 1000ms, 错误率 < 0.1%, 可用性 99.9% |

### 3.2 流量模型设计

#### 业务场景梳理

| 业务场景 | 接口 | 日常比例 | 大促比例 | 预期QPS |
|----------|------|----------|----------|---------|
| 首页浏览 | GET /home | 40% | 35% | 350 |
| 商品搜索 | GET /search | 20% | 25% | 250 |
| 商品详情 | GET /product/{id} | 25% | 20% | 200 |
| 加入购物车 | POST /cart | 10% | 12% | 120 |
| 下单支付 | POST /order | 4% | 6% | 60 |
| 个人中心 | GET /profile | 1% | 2% | 20 |

#### 流量模型图

```
              ┌────▼─────────▼────┐

              ┌────────▼──────────┐
              │    下单支付        │
```

### 3.3 数据量要求

| 数据类型 | 数量 | 说明 |
|----------|------|------|
| 测试用户 | 10,000 | 模拟真实用户基数 |
| 商品 SKU | 50,000 | 足够的数据量避免缓存全命中 |
| 历史订单 | 1,000,000 | 模拟真实数据库大小 |
| 购物车数据 | 50,000 | 每个活跃用户有购物车 |

### 3.4 场景设计

| 阶段 | 时长 | 线程数 | QPS | 说明 |
|------|------|--------|-----|------|
| 预热 | 5 min | 0→200 | 0→200 | 逐步加压 |
| 基准 | 10 min | 200 | 200 | 稳态基线 |
| 加压 | 10 min | 200→500 | 200→500 | 模拟增长 |
| 峰值 | 15 min | 500→1000 | 500→1000 | 最大压力 |
| 降压 | 5 min | 1000→0 | 1000→0 | 逐步降压 |

**总时长：** 约 45 分钟

## 4. 阶段二：脚本开发

### 4.1 接口梳理清单

| 接口 | 方法 | 路径 | 依赖数据 | 提取数据 |
|------|------|------|----------|----------|
| 首页 | GET | `/home` | - | - |
| 搜索 | GET | `/search?q={keyword}` | 搜索词CSV | - |
| 商品详情 | GET | `/product/{id}` | 商品ID（从搜索提取） | productId |
| 加购 | POST | `/cart` | userId, productId | cartId |
| 下单 | POST | `/order` | userId, cartId | orderId |
| 支付 | POST | `/pay` | userId, orderId | paymentId |
| 个人中心 | GET | `/profile` | userId | - |

### 4.2 脚本结构

```

│
├── User Defined Variables
│   ├── ENV = ${__P(env,staging)}
│   ├── BASE_URL = ${__P(base_url,api.example.com)}
│   └── THINK_TIME = ${__P(think_time,500)}
│
├── setUp Thread Group (1 thread)
│   ├── POST - 批量创建测试用户
│   ├── POST - 批量创建商品
│   ├── POST - 初始化库存
│   └── JSR223 Sampler: 记录初始化完成标记
│
├── HTTP Request Defaults

│   └── Content-Type: application/json
│
├── Thread Group: 浏览类 (40 threads)
│   ├── Uniform Random Timer (${THINK_TIME}ms ± 200ms)

│   └── Throughput Controller (40%) → GET 分类页
│
├── Thread Group: 搜索类 (25 threads)

│
├── Thread Group: 详情类 (20 threads)

│   │   └── GET 商品详情
│   └── ...
│
├── Thread Group: 交易类 (15 threads)
│   ├── Uniform Random Timer (${THINK_TIME}ms ± 200ms)
│   ├── CSV Data Set Config: users.csv
│   ├── Transaction Controller: 完整交易
│   │   ├── POST 登录 → 提取 token
│   │   ├── POST 加购 → 提取 cartId

│   └── ...

├── tearDown Thread Group (1 thread)
│   ├── POST 清理测试数据

│

│   └── influxdbUrl: http://monitor:8086/write?db=jmeter

└── Aggregate Report
```

### 5.2 Slave 节点配置

**jmeter.properties** 关键配置：

```properties
# Slave 模式
server.rmi.ssl.disable=true
server.rmi.port=1099
server.rmi.localport=1099

# 禁用 SSL（仅测试环境）
server.rmi.ssl.disable=true
```

**启动 Slave：**

```bash
# 在每个 Slave 节点上
jmeter-server -Djava.rmi.server.hostname=<slave_ip>

# 后台运行
nohup jmeter-server -Djava.rmi.server.hostname=<slave_ip> &
```

### 5.3 Master 节点执行

```bash
# 分布式执行
jmeter -n \
    -t full_link_test.jmx \
    -R slave1_ip,slave2_ip,slave3_ip \
    -Jenv=staging \
    -Jthreads=600 \
    -Jduration=2700 \
    -l results/full_link_$(date +%Y%m%d_%H%M%S).csv \
    -e -o reports/full_link_$(date +%Y%m%d_%H%M%S)
```

## 6. 阶段四：执行监控

### 6.1 执行时序

```
时间轴:
00:00 ─ 开始预热
05:00 ─ 进入基准阶段 (200 QPS)
15:00 ─ 开始加压 (200→500 QPS)
25:00 ─ 进入峰值阶段 (500→1000 QPS)
40:00 ─ 开始降压
45:00 ─ 测试结束
```

### 6.2 实时监控面板

使用 Grafana 创建监控面板：

#### JMeter 指标面板

| 图表 | 指标 | 告警阈值 |
|------|------|----------|
| Active Threads | 活跃线程数 | - |
| Response Time (avg, P90, P95, P99) | 响应时间 | P99 > 2000ms |
| Transactions/sec | 吞吐量 | 低于目标 QPS 20% |
| Error Rate | 错误率 | > 1% |
| Bytes/sec | 网络流量 | - |

#### 系统指标面板

| 图表 | 指标 | 告警阈值 |
|------|------|----------|
| CPU Usage | CPU 使用率 | > 80% |
| Memory Usage | 内存使用率 | > 85% |
| Disk IO | 磁盘读写 | - |
| Network IO | 网络吞吐 | - |

#### 数据库指标

| 图表 | 指标 | 告警阈值 |
|------|------|----------|
| Connections | 活跃连接数 | > 80% 最大连接 |
| QPS | 数据库 QPS | - |
| Slow Queries | 慢查询数 | > 10/min |
| Lock Waits | 锁等待 | > 5 |

### 6.3 实时决策

| 观察到的现象 | 决策 |
|-------------|------|
| 错误率 > 5% | **立即停止**，排查根因 |
| 错误率 1-5% | 记录日志，继续观察 |
| P99 RT 超过 SLA 3倍 | **暂停加压**，观察恢复 |
| CPU 持续 > 90% | 记录为瓶颈，继续但不再加压 |
| 数据库连接池耗尽 | **立即停止** |
| 目标 QPS 未达到但资源充足 | 增加线程数 |

### 6.4 异常处理流程

```
发现异常
    ├── 错误率 > 5% → 立即停止 → 保存现场 → 分析日志
    ├── RT 飙升 → 暂停加压 → 观察5分钟
    │   ├── 恢复 → 继续加压
    │   └── 未恢复 → 降级 → 记录瓶颈点
    ├── 资源耗尽 → 立即停止 → 检查资源泄漏
    └── 目标未达成 → 增加资源 → 重新测试
```

### 7.2 分析维度

#### 吞吐量分析

| 阶段 | 目标 QPS | 实际 QPS | 达成率 |
|------|----------|----------|--------|
| 基准 | 200 | 198 | 99% |
| 加压 | 500 | 485 | 97% |
| 峰值 | 1000 | 920 | 92% |

> 峰值阶段 QPS 未完全达标，说明系统在 920 QPS 左右达到瓶颈。

#### 响应时间分析

| 阶段 | Avg RT | P90 RT | P99 RT | SLA 达标 |
|------|--------|--------|--------|----------|
| 基准 | 120ms | 200ms | 350ms | ✅ |
| 加压 | 280ms | 500ms | 900ms | ✅ |
| 峰值 | 450ms | 850ms | 1800ms | ❌ P99 超标 |

#### 错误分析

| 错误类型 | 数量 | 占比 | 出现阶段 |
|----------|------|------|----------|
| 502 Bad Gateway | 150 | 45% | 峰值 |
| Connection Timeout | 120 | 36% | 峰值 |
| 500 Internal Error | 60 | 18% | 加压/峰值 |
| 其他 | 5 | 1% | 分散 |

#### 资源分析

| 资源 | 基准 | 加压 | 峰值 | 瓶颈? |
|------|------|------|------|-------|
| App CPU | 40% | 65% | 88% | ⚠️ 接近瓶颈 |
| App Memory | 60% | 72% | 78% | ✅ 正常 |
| DB CPU | 30% | 55% | 82% | ⚠️ 接近瓶颈 |
| DB Connections | 50 | 120 | 190/200 | ❌ 瓶颈 |
| Redis Memory | 2GB | 3.5GB | 5.8GB/8GB | ✅ 正常 |

### 7.3 瓶颈定位

**主要瓶颈：数据库连接池**
- 最大连接数 200，峰值使用 190
- 建议：增加到 400 或使用连接池优化

**次要瓶颈：应用 CPU**
- 峰值 88%，接近告警线
- 建议：增加实例或优化代码

### 7.4 优化建议

| 优先级 | 问题 | 建议 | 预期提升 |
|--------|------|------|----------|
| P0 | 数据库连接池不足 | 增加到 400 | QPS +15% |
| P1 | 502 错误（超时） | 调整 LB 超时配置 | 错误率 -30% |
| P2 | 应用 CPU 高 | 增加 2 个实例 | QPS +20% |
| P3 | P99 RT 高 | 排查慢查询和 GC | RT -30% |

## 9. 风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| 压测影响生产 | 低 | 高 | 使用独立环境，流量隔离 |
| 数据污染 | 中 | 中 | 使用测试数据前缀，tearDown清理 |
| 监控数据丢失 | 低 | 中 | 多重监控（JMeter+Grafana+APM） |
| Slave 节点宕机 | 中 | 中 | 冗余 Slave，自动剔除 |
| 网络瓶颈 | 低 | 高 | 确保 Slave 和目标系统在同一网段 |
| 压测结果不准确 | 中 | 高 | 多轮测试取中位数，预热充分 |

## 10. 常见问题排查

### 10.1 分布式测试中 Slave 连接失败

**解决：**
1. 检查 `server.rmi.ssl.disable=true`
2. 检查防火墙规则（RMI 端口 1099）
3. 检查 `java.rmi.server.hostname` 设置

### 10.2 压测结果文件过大

**解决：** 配置 `jmeter.save.saveservice.*` 属性，只保存必要字段：

```properties
jmeter.save.saveservice.output_format=csv
jmeter.save.saveservice.response_data=false
jmeter.save.saveservice.samplerData=false
jmeter.save.saveservice.response_headers=false
jmeter.save.saveservice.request_headers=false
```

### 10.3 压测过程中数据量不够

**解决：**
1. 使用 `Recycle on EOF = True` 循环使用 CSV 数据
2. 使用 `__Random()` / `__RandomString()` 函数生成动态数据
3. setUp Thread Group 中批量创建测试数据
