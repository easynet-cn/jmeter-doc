# 07 - 混合负载与多场景并发

> **难度：★★★★☆** | **适用版本：JMeter 5.6.3** | **预计阅读：25分钟**

---

## 1. 场景概述

单场景压测只能反映系统的局部性能。真实生产环境往往是多种业务混合并发。本章教你构建接近生产真实流量的混合负载测试。

**你将学到：**
- 多线程组混合并发配置
- 业务比例分配策略
- setUp/tearDown Thread Group 使用
- Constant Throughput Timer 精准控速
- 阶梯加压（Stepping Load）
- Synchronizing Timer 集合点（Spike Test）
- Open Model Thread Group 高级用法

---

## 2. 多线程组混合并发

### 2.1 场景：电商混合流量

**业务比例：**
- 浏览首页：50%
- 搜索商品：25%
- 商品详情：15%
- 加入购物车：7%
- 下单支付：3%

### 2.2 方式一：多线程组（推荐）

```
Test Plan
├── setUp Thread Group
│   └── POST - 初始化测试数据
├── Thread Group: 浏览首页 (50 threads)
│   ├── Constant Throughput Timer: 50/秒
│   └── GET - 首页
├── Thread Group: 搜索 (25 threads)
│   ├── Constant Throughput Timer: 25/秒
│   └── GET - 搜索
├── Thread Group: 商品详情 (15 threads)
│   ├── Constant Throughput Timer: 15/秒
│   └── GET - 商品详情
├── Thread Group: 加购 (7 threads)
│   ├── Constant Throughput Timer: 7/秒
│   └── POST - 加入购物车
├── Thread Group: 下单 (3 threads)
│   ├── Constant Throughput Timer: 3/秒
│   └── Transaction Controller: 下单流程
└── tearDown Thread Group
    └── POST - 清理测试数据
```

### 2.3 线程组配置

| Thread Group | Threads | Ramp-up | Duration | 说明 |
|-------------|---------|---------|----------|------|
| 浏览首页 | `50` | `30s` | `600s` | 基准负载 |
| 搜索 | `25` | `30s` | `600s` | 中负载 |
| 商品详情 | `15` | `30s` | `600s` | 中负载 |
| 加购 | `7` | `30s` | `600s` | 低负载 |
| 下单 | `3` | `30s` | `600s` | 低负载 |

> **注意：** 勾选 Thread Group 的 "Run Thread Groups consecutively" 为 **False**，确保所有线程组**同时运行**。

### 2.4 方式二：单线程组 + Throughput Controller

```
Thread Group (100 threads)
├── Throughput Controller (50%)
│   └── GET - 浏览首页
├── Throughput Controller (25%)
│   └── GET - 搜索
├── Throughput Controller (15%)
│   └── GET - 商品详情
├── Throughput Controller (7%)
│   └── POST - 加入购物车
└── Throughput Controller (3%)
    └── Transaction Controller: 下单流程
```

### 2.5 方式对比

| 对比维度 | 多线程组 | 单线程组+Throughput |
|----------|---------|---------------------|
| 比例精确度 | ★★★★★ | ★★★☆☆ |
| 独立配置灵活性 | ★★★★★ | ★★☆☆☆ |
| 独立阶梯加压 | ★★★★★ | ★☆☆☆☆ |
| 配置简洁度 | ★★★☆☆ | ★★★★★ |
| 适用场景 | 精确比例、独立监控 | 简单流量分配 |

> **推荐：** 需要精确控制比例和独立阶梯加压时使用多线程组。快速验证时用单线程组+Throughput Controller。

## 3. setUp / tearDown Thread Group

### 3.1 setUp Thread Group

在所有常规线程组之前执行，用于**初始化**：

```
setUp Thread Group
├── POST - 批量创建测试用户
├── POST - 初始化商品库存
├── POST - 登录获取Admin Token
└── JSR223 Sampler: 写入初始化标记
```

### 3.2 tearDown Thread Group

在所有常规线程组之后执行，用于**清理**：

```
tearDown Thread Group
├── POST - 清理测试订单
├── POST - 删除测试用户
├── POST - 恢复商品库存
└── POST - 登出
```

### 3.3 注意事项

- setUp/tearDown 线程数通常设为 **1**
- 确保 tearDown 中有充分的错误处理
- 可使用 `__setProperty()` 和 `__property()` 在 setUp 和常规线程组间传递数据

**setUp 写入属性：**

```groovy
// JSR223 Sampler in setUp
props.put("adminToken", adminToken)
props.put("testStartTime", String.valueOf(System.currentTimeMillis()))
```

**常规线程组读取：**

```
${__property(adminToken)}
${__property(testStartTime)}
```

## 4. Constant Throughput Timer（精准控速）

### 4.1 基本配置

| 参数 | 说明 |
|------|------|
| Target Throughput (samples/minute) | 目标吞吐量（每分钟采样数） |
| Calculate Throughput based on | 计算基准 |

### 4.2 计算基准选择

| 选项 | 说明 |
|------|------|
| **this thread only** | 每个线程独立计算 |
| **all active threads in current thread group** | 当前线程组所有线程共享 |
| **all active threads** | 全局所有线程共享 |
| **all active threads (shared)** | 全局共享（精确） |

### 4.3 吞吐量换算

```
目标 QPS = N 次/秒
每分钟吞吐量 = N × 60

例如：100 QPS = 6000 samples/minute
```

### 4.4 实战：精准控制各业务 QPS

```
Thread Group: 浏览 (50 threads)
└── Constant Throughput Timer
    ├── Target Throughput: 6000  ← 100 QPS = 6000/min
    └── Based on: all active threads in current thread group

Thread Group: 搜索 (25 threads)
└── Constant Throughput Timer
    ├── Target Throughput: 3000  ← 50 QPS
    └── Based on: all active threads in current thread group
```

### 4.5 Precise Throughput Timer

比 Constant Throughput Timer 更精确（JMeter 4.0+），但需要足够的线程数。

| 参数 | 说明 |
|------|------|
| Target Throughput | 目标吞吐量 |
| Throughput Period | 周期（秒） |
| Test Duration | 持续时间 |
| Number of threads in the bath | 批处理线程数 |

## 5. 阶梯加压（Stepping Load）

### 5.1 场景

逐步增加负载，观察系统在不同压力级别下的表现，找到性能拐点。

### 5.2 使用 Stepping Thread Group（JMeter Plugin）

需要安装 **Custom Thread Groups** 插件（`jpgc-casutg`）：

```
Stepping Thread Group
├── This group will start: 100 threads
├── First, wait for: 0 seconds
├── Then start: 20 threads         ← 每步增加20线程
├── Next, add: 20 threads every: 60 seconds  ← 每60秒加20线程
├── Using ramp-up: 10 seconds      ← 每次增加用时10秒
├── Then hold load for: 60 seconds ← 每级保持60秒
└── Finally, stop: 20 threads every: 5 seconds ← 逐步停止
```

**加压曲线：**

```
线程数
100 |                              ████████
80  |                        ██████
60  |                  ██████
40  |            ██████
20  |      ██████
0   |──────┴──────┴──────┴──────┴──────┴──────→ 时间
    0     60     120    180    240    300
```

### 5.3 无插件阶梯加压

如果没有插件，可用命令行分批执行：

```bash
#!/bin/bash
# 阶梯加压脚本
for threads in 20 40 60 80 100; do
    echo "=== 阶梯: ${threads} 线程 ==="
    jmeter -n -t test.jmx \
        -Jthreads=$threads \
        -Jrampup=10 \
        -Jduration=120 \
        -l results/step_${threads}.csv \
        -e -o reports/step_${threads}
    sleep 10  # 间隔10秒
done
```

## 6. Synchronizing Timer（集合点 / Spike Test）

### 6.1 场景

模拟瞬时高并发：让所有线程在某一时刻同时发起请求。

### 6.2 基本配置

| 参数 | 说明 |
|------|------|
| Number of Simulated Users to Group by | 集合多少线程后释放 |
| Timeout in milliseconds | 超时时间（防止无限等待） |

### 6.3 实战：秒杀场景

```
POST - 秒杀下单
├── Synchronizing Timer
│   ├── Group by: 100            ← 凑齐100个线程
│   └── Timeout: 5000            ← 最多等5秒
└── ...
```

### 6.4 注意事项

- **必须确保线程数 ≥ Group by 数量**，否则可能永远凑不齐
- Timeout 设得太大会让部分线程长时间阻塞
- 集合点前可以加一个等待点，确保所有线程都就位

## 7. Open Model Thread Group（JMeter 5.5+）

### 7.1 与传统线程组的区别

传统线程组是**闭环模型**（固定线程数），Open Model Thread Group 是**开环模型**（固定到达速率），更接近真实用户行为。

### 7.2 基本配置

```
Open Model Thread Group
├── Rate: 100/sec          ← 每秒到达100个用户
├── Duration: 600s         ← 持续10分钟
├── Random seed: 0
└── ...
```

### 7.3 到达速率模式

| 模式 | 说明 | 示例 |
|------|------|------|
| `rate(100/sec)` | 固定速率 | 每秒100用户 |
| `rate(0/sec) random_arrivals(10 min)` | 随机到达 | 10分钟总到达量 |
| `rate(0/sec) even_arrivals(10 min)` | 均匀到达 | 10分钟均匀分布 |

### 7.4 多阶段场景

```
Open Model Thread Group
Schedule:
  rate(0/sec) random_arrivals(120 sec)   # 预热：2分钟随机到达
  rate(100/sec) for 300 sec              # 稳定：100/s持续5分钟
  rate(200/sec) for 180 sec              # 峰值：200/s持续3分钟
  rate(0/sec) for 60 sec                 # 冷却：停止到达1分钟
```

## 8. 综合实战：完整电商压测方案

### 8.1 测试场景设计

| 阶段 | 时长 | 目标QPS | 线程数 | 说明 |
|------|------|---------|--------|------|
| 预热 | 120s | 0→200 | 0→100 | 逐步加压 |
| 基准 | 300s | 200 | 100 | 稳态运行 |
| 峰值 | 180s | 400 | 200 | 2倍负载 |
| 冷却 | 60s | 200→0 | 100→0 | 逐步降压 |

### 8.2 完整测试计划

```
Test Plan: 电商全链路压测
│

│   └── env = ${__P(env,staging)}
│

│   ├── POST - 创建100个测试用户

│   └── JSR223 Sampler: props.put("ready", "true")

├── Thread Group: 浏览流量 (50 threads)
│   ├── Constant Throughput Timer: 6000/min (100 QPS)
│   ├── GET - 首页
│   ├── GET - 分类页
│   └── GET - 商品详情
│
├── Thread Group: 搜索流量 (25 threads)
│   ├── Constant Throughput Timer: 3000/min (50 QPS)
│   ├── CSV Data Set Config: search_terms.csv
│   └── GET - 搜索
│       └── Parameters: q = ${searchTerm}
│
├── Thread Group: 交易流量 (25 threads)
│   ├── Constant Throughput Timer: 3000/min (50 QPS)
│   ├── CSV Data Set Config: users.csv
│   ├── Transaction Controller: 下单流程
│   │   ├── POST - 登录
│   │   │   └── JSON Extractor → token, userId
│   │   ├── GET - 商品详情
│   │   ├── POST - 加入购物车
│   │   ├── POST - 创建订单
│   │   │   └── JSON Extractor → orderId
│   │   ├── POST - 支付
│   │   └── GET - 订单确认

├── tearDown Thread Group (1 thread)
│   ├── POST - 取消所有测试订单
```

## 9. 常见问题排查

### 9.1 线程组没有并发执行

**解决：** Test Plan 中取消勾选 "Run Thread Groups consecutively"。

### 9.2 实际 QPS 达不到目标

**排查：**
1. 检查线程数是否足够（线程数 ≥ QPS × 平均响应时间）
2. 检查 Constant Throughput Timer 的 Calculate Based on 设置
3. 检查网络带宽是否瓶颈
4. 检查 JMeter 所在机器资源（CPU/内存）

### 9.3 Synchronizing Timer 线程一直阻塞

**解决：**
1. 确保 Group by ≤ 线程总数
2. 设置合理的 Timeout
3. 如果部分线程被 If Controller 跳过，可改用 `all active threads in current thread group` 模式

### 9.4 阶梯加压效果不明显

**原因：** 响应时间太短，线程还没来得及全部启动就已经完成请求。

**解决：** 增加 Ramp-up 时间，或使用 Stepping Thread Group 插件精确控制。
