# 06 - 断言策略与错误处理

> **难度：★★★☆☆** | **适用版本：JMeter 5.6.3** | **预计阅读：20分钟**

---

## 1. 场景概述

没有断言的性能测试等于"盲测"——你可能在压测一个已经报错的系统而不自知。本章建立完整的断言体系，确保每次压测的数据都是可信的。

**你将学到：**
- Response Assertion 多层组合
- JSON Assertion 精确验证
- Duration Assertion 响应时间校验
- Size Assertion 响应大小检查
- JSR223 Assertion 自定义断言逻辑
- 断言失败后的处理策略
- 性能测试中的断言最佳实践

---

## 2. 断言体系设计原则

```
        ┌─────────────────────────────────┐
        │          HTTP Status Code       │  ← 第一层：状态码
        │         (Response Assertion)     │
        ├─────────────────────────────────┤
        │      业务 Code & Message        │  ← 第二层：业务正确性
        │         (JSON Assertion)         │
        ├─────────────────────────────────┤
        │      关键数据完整性              │  ← 第三层：数据验证
        │   (JSON/Response Assertion)      │
        ├─────────────────────────────────┤
        │      响应时间 SLA               │  ← 第四层：性能SLA
        │      (Duration Assertion)        │
        ├─────────────────────────────────┤
        │      响应大小                    │  ← 第五层：异常检测
        │       (Size Assertion)           │
        └─────────────────────────────────┘
```

## 3. Response Assertion（响应断言）

### 3.1 基本配置

| 参数 | 说明 |
|------|------|
| Apply to | 应用到哪个范围 |
| Field to Test | 测试哪个字段 |
| Pattern Matching Rules | 匹配规则 |
| Patterns to Test | 匹配模式列表 |

### 3.2 匹配规则详解

| 规则 | 说明 | 示例 |
|------|------|------|
| **Contains** | 响应包含指定文本 | 检查是否包含 `"success"` |
| **Matches** | 正则匹配 | 检查是否匹配 `\d+` |
| **Equals** | 完全相等 | 检查是否等于 `OK` |
| **Substring** | 子字符串 | 同 Contains |
| **Not** | 取反（可与上述组合） | 不包含 `"error"` |
| **Or** | 或逻辑 | 包含 A 或 B |

### 3.3 实战：HTTP 状态码断言

```
Response Assertion
├── Apply to: Main sample only
├── Field to Test: Response Code
├── Pattern Matching: Equals
└── Patterns: 200
```

### 3.4 实战：多层组合断言

**场景：** 确保登录 API 返回正确结果。

```
POST - 登录
├── Response Assertion: 状态码
│   ├── Field: Response Code
│   ├── Pattern Matching: Equals
│   └── Patterns: 200
├── Response Assertion: 响应体包含
│   ├── Field: Text Response
│   ├── Pattern Matching: Contains
│   └── Patterns: "code":200
├── Response Assertion: 不包含错误
│   ├── Field: Text Response
│   ├── Pattern Matching: Not
│   └── Patterns: "error"
└── Response Assertion: 正则匹配
    ├── Field: Text Response
    ├── Pattern Matching: Matches
    └── Patterns: "token":"[A-Za-z0-9._-]+"
```

### 3.5 响应头断言

```
Response Assertion
├── Field to Test: Response Headers
├── Pattern Matching: Contains
└── Patterns: Content-Type: application/json
```

## 4. JSON Assertion（JSON 断言）

### 4.1 基本配置

| 参数 | 说明 |
|------|------|
| JSON Path | 要检查的 JSONPath |
| Additionally assert value | 是否额外断言值 |
| Expected Value | 期望值 |
| Expect null | 是否期望 null |
| Invert assertion | 是否取反 |

### 4.2 实战：精确验证响应结构

**响应 JSON：**

```json
{
    "code": 200,
    "message": "success",
    "data": {
        "user": {
            "id": 12345,
            "name": "John Doe",
            "roles": ["USER", "ADMIN"]
        }
    }
}
```

**断言配置：**

| JSON Path | Expected Value | 说明 |
|-----------|---------------|------|
| `$.code` | `200` | 业务状态码 |
| `$.message` | `success` | 消息 |
| `$.data.user.name` | （不填） | 确保字段存在 |
| `$.data.user.roles[0]` | `USER` | 第一个角色 |

### 4.3 实战：验证数组长度

```
JSON Assertion
├── JSON Path: $.data.items
├── Additionally assert value: ✓
├── Expected Value: （不填，仅验证存在）
```

配合 JSR223 Assertion 验证长度：

```groovy
def json = new groovy.json.JsonSlurper().parse(prev.getResponseData())
def items = json.data.items
if (items.size() == 0) {
    AssertionResult.setFailure(true)
    AssertionResult.setFailureMessage("商品列表为空")
}
```

### 4.4 实战：验证数组元素属性

```
JSON Assertion
├── JSON Path: $.data.items[0].id
├── Additionally assert value: ✓
└── Expected Value: （不填，验证第一个元素有 id 字段）
```

## 5. JSON JMESPath Assertion

### 5.1 优势

JMESPath 比 JSONPath 更适合复杂条件验证。

### 5.2 实战：验证所有商品都有价格

```
JSON JMESPath Assertion
├── JMESPath: length(data.items[?price == null || price == ''])
└── Expected Value: 0
```

### 5.3 实战：验证排序正确

```
JSON JMESPath Assertion
├── JMESPath: data.items == sort_by(data.items, &price)
└── Expected Value: true
```

## 6. Duration Assertion（响应时间断言）

### 6.1 基本配置

| 参数 | 值 |
|------|-----|
| Duration (ms) | 最大允许响应时间 |

### 6.2 实战：SLA 分层断言

```
POST - 创建订单 (核心接口)
├── Duration Assertion: 2000ms  ← 核心接口 2s SLA
├── Duration Assertion: 5000ms  ← 如果超过5s则记录严重告警
└── ...
```

### 6.3 配合 JSR223 实现分级告警

```groovy
def elapsed = prev.getTime()
def label = prev.getSampleLabel()

if (elapsed > 5000) {
    log.error("严重: ${label} 响应时间 ${elapsed}ms > 5000ms")
    vars.put("alertLevel", "CRITICAL")
} else if (elapsed > 2000) {
    log.warn("警告: ${label} 响应时间 ${elapsed}ms > 2000ms")
    vars.put("alertLevel", "WARNING")
} else {
    vars.put("alertLevel", "OK")
}
```

## 7. Size Assertion（响应大小断言）

### 7.1 基本配置

| 参数 | 说明 |
|------|------|
| Response Size Field | Full Response / Response Headers / Response Body / Response Code / Response Message |
| Compare with | = / ≠ / > / < / ≥ / ≤ |
| Size to Assert (bytes) | 阈值 |

### 7.2 实战：检测异常小响应

```
Size Assertion
├── Response Size Field: Response Body
├── Compare with: >
└── Size to Assert: 100
```

> 如果响应体小于 100 字节，可能是返回了错误页面而非正常数据。

### 7.3 实战：检测异常大响应

```
Size Assertion
├── Response Size Field: Response Body
├── Compare with: <
└── Size to Assert: 1048576
```

> 限制 1MB，防止单个响应过大影响性能。

## 8. JSR223 Assertion（自定义断言）

### 8.1 适用场景

当内置断言无法满足时（如跨字段验证、数据库对比、复杂计算）。

### 8.2 实战：响应数据与请求数据一致性校验

```groovy
import groovy.json.JsonSlurper

def response = new JsonSlurper().parseText(prev.getResponseDataAsString())
def requestBody = new JsonSlurper().parseText(sampler.getArguments().getArgument(0).getValue())

// 验证请求的 userId 与响应的 userId 一致
def requestUserId = requestBody.userId.toString()
def responseUserId = response.data.userId.toString()

if (requestUserId != responseUserId) {
    AssertionResult.setFailure(true)
    AssertionResult.setFailureMessage(
        "数据不一致: 请求userId=${requestUserId}, 响应userId=${responseUserId}"
    )
}
```

### 8.3 实战：验签

```groovy
import java.security.MessageDigest

def response = prev.getResponseDataAsString()
def responseJson = new groovy.json.JsonSlurper().parseText(response)

def data = responseJson.data
def expectedSign = responseJson.sign

// 计算签名
def content = "${data.orderId}${data.amount}${data.timestamp}SECRET_KEY"
def md = MessageDigest.getInstance("MD5")
def calculatedSign = md.digest(content.bytes).encodeHex().toString()

if (calculatedSign != expectedSign) {
    AssertionResult.setFailure(true)
    AssertionResult.setFailureMessage("签名验证失败")
}
```

### 8.4 实战：业务逻辑校验

```groovy
import groovy.json.JsonSlurper

def json = new JsonSlurper().parseText(prev.getResponseDataAsString())

// 订单金额校验
def totalAmount = json.data.totalAmount as double
def items = json.data.items

def calculatedAmount = items.sum { item ->
    (item.price as double) * (item.quantity as int)
}

if (Math.abs(totalAmount - calculatedAmount) > 0.01) {
    AssertionResult.setFailure(true)
    AssertionResult.setFailureMessage(
        "金额不匹配: 系统=${totalAmount}, 计算=${calculatedAmount}"
    )
}
```

## 9. 断言失败处理策略

### 9.1 策略对比

| 策略 | 配置方式 | 适用场景 |
|------|----------|----------|
| **仅记录** | 默认行为 | 开发调试阶段 |
| **停止线程** | Flow Control Action | 该用户后续操作无意义 |
| **停止线程组** | Result Status Action Handler | 关键流程失败 |
| **停止测试** | Result Status Action Handler | 致命错误 |

### 9.2 Flow Control Action

右键采样器 → Add → Sampler → **Flow Control Action**

| 参数 | 值 | 说明 |
|------|-----|------|
| Target | `Current Thread` | 停止当前线程 |
| Action | `Stop` / `Pause` / `Start Next Loop` | 动作 |
| Duration (ms) | `0` | 暂停时长 |

### 9.3 实战：登录失败 → 停止线程

```
POST - 登录
├── Response Assertion (状态码: 200)
├── If Controller (条件: !${JMeterThread.last_sample_ok})
│   ├── JSR223 Sampler: log.error("登录失败，停止线程")
│   └── Flow Control Action (Stop Current Thread)
└── JSON Extractor → token
```

## 10. 性能测试断言最佳实践

### 10.1 开发阶段（全量断言）

```diff
+ 每个采样器都添加断言
+ 断言内容尽可能详细
+ 失败时立即停止
```

### 10.2 负载测试阶段（精简断言）

```diff
- 减少断言数量（断言本身消耗资源）
+ 仅保留关键业务断言
+ 使用 Duration Assertion 监控 SLA
+ 不停止线程（仅记录错误率）
```

**推荐配置：**

| 场景 | 保留的断言 |
|------|-----------|
| 登录 | Response Code + Token 存在性 |
| 创建订单 | Response Code + 订单ID 存在性 |
| 查询 | Response Code + 响应大小 |
| 所有 | Duration Assertion (SLA) |

### 10.3 断言性能影响

```
断言的 CPU 开销排序（从低到高）：
1. Duration Assertion        ← 几乎无开销
2. Size Assertion            ← 几乎无开销
3. Response Assertion        ← 低开销（简单模式匹配）
4. JSON Assertion            ← 中等开销（需解析JSON）
5. JSR223 Assertion          ← 高开销（脚本引擎）
```

> **建议：** 压测时移除 JSR223 Assertion 和复杂的 JSON Assertion，仅保留必要的 Response/Duration Assertion。

### 10.4 忽略特定错误

```
Response Assertion
├── Field: Response Code
├── Pattern Matching: Equals
├── Patterns: 200
└── Ignore Status: ✓  ← 勾选后不影响 JMeter 采样状态
```

> 注意：Ignore Status 勾选后，即使断言失败，采样器也标记为成功。一般不推荐使用。

## 11. 常见问题排查

### 11.1 断言始终失败

**排查步骤：**
1. View Results Tree 查看实际响应内容
2. 检查 Response Assertion 的 Field to Test 是否正确
3. 检查 JSONPath 表达式（使用 JSON Path Tester）
4. 确认编码方式（ResponseBody 可能是乱码）

### 11.2 断言通过了但数据不对

**原因：** 断言不够严格。如仅检查 `Contains: success`，但响应是 `"success":false`。

**解决：** 使用更精确的断言方式：
```
JSON Assertion + Expected Value: true
// 而非
Response Assertion + Contains: success
```

### 11.3 压测时断言导致吞吐量下降

**解决：**
1. 移除复杂的 JSR223 Assertion
2. 减少 JSON Assertion 数量
3. 使用 Size Assertion 替代 Response Assertion（Contains 模式）
4. 仅在关键采样器上保留断言
