## 2. 性能基准线（Baseline）

### 2.1 什么是性能基准线

在**最小负载**下（如 1-5 并发），测量系统的最优性能表现，作为后续对比的参考。

### 2.2 基准测试配置

```
Thread Group: 基准测试
├── Threads: 1 → 3 → 5 (分三轮)
├── Ramp-up: 1s
├── Duration: 120s (稳定运行)
├── Loop: Forever (配合Duration)
└── Constant Throughput Timer: 无 (让系统自由发挥)
```

### 2.3 基准测试执行

```bash
#!/bin/bash
# 基准测试脚本
for threads in 1 3 5; do
    echo "=== 基准测试: ${threads} 线程 ==="
    jmeter -n \
        -t baseline_test.jmx \
        -Jthreads=$threads \
        -Jduration=120 \
        -l results/baseline_${threads}vu.csv \
        -e -o reports/baseline_${threads}vu
done
```

### 2.4 基准指标记录

| 指标 | 1 VU | 3 VU | 5 VU | 说明 |
|------|------|------|------|------|
| 平均响应时间 (ms) | 45 | 48 | 52 | 低负载最优RT |
| P90 响应时间 (ms) | 60 | 65 | 70 | - |
| P99 响应时间 (ms) | 85 | 95 | 110 | - |
| 吞吐量 (QPS) | 22 | 62 | 96 | 随VU线性增长 |
| 错误率 (%) | 0 | 0 | 0 | - |

> **结论：** 在低负载下，系统单 VU 吞吐约 22 QPS，5 VU 约 96 QPS（接近线性扩展）。

## 3. 逐步加压找拐点

### 3.1 什么是性能拐点

当增加负载时，系统从**线性扩展**转变为**亚线性扩展**甚至**性能下降**的临界点。

### 3.2 加压方案

```
压力阶梯:
┌──────────┬─────────┬──────────┐
│ 阶梯     │ 线程数  │ 持续时间  │
├──────────┼─────────┼──────────┤
│ 预热     │ 10      │ 120s     │
│ 阶梯1    │ 50      │ 300s     │
│ 阶梯2    │ 100     │ 300s     │
│ 阶梯3    │ 200     │ 300s     │
│ 阶梯4    │ 500     │ 300s     │
│ 阶梯5    │ 1000    │ 300s     │
│ 冷却     │ 0       │ 60s      │
└──────────┴─────────┴──────────┘
```

### 3.3 自动化加压脚本

```bash
#!/bin/bash
# 阶梯加压脚本
STEPS=(10 50 100 200 500 1000)
DURATION=300

for step in "${STEPS[@]}"; do
    echo "=========================================="
    echo " 阶梯: ${step} VU, 持续 ${DURATION}s"
    echo "=========================================="
    
    jmeter -n \
        -t capacity_test.jmx \
        -Jthreads=$step \
        -Jrampup=30 \
        -Jduration=$DURATION \
        -l "results/capacity_${step}vu.csv" \
        -e -o "reports/capacity_${step}vu"
    
    # 检查是否已经出现严重错误
    ERROR_RATE=$(jq '.Total.errorPct' "reports/capacity_${step}vu/statistics.json")
    if (( $(echo "$ERROR_RATE > 5.0" | bc -l) )); then
        echo "⚠️  错误率超过5%，停止加压"
        break
    fi
done
```

### 3.4 拐点分析

```
吞吐量
(QPS)
 500 |                              ●  ← 最大吞吐量 (500 QPS @ 500 VU)
     |                          ●
 400 |                      ●        ← 拐点区 (300-400 QPS @ 200 VU)
     |                  ●
 300 |              ●
     |          ●
 200 |      ●
     |  ●
 100 |●                               ← 线性扩展区
     |
   0 └─────┴─────┴─────┴─────┴──────→ 线程数
    10    50    100   200   500   1000

响应时间
(ms)
3000 |                              ●  ← 响应时间暴涨
     |                          ●
2000 |                      ●
     |                  ●
1000 |              ●               ← 拐点
     |          ●
 500 |      ●
     |  ●
 200 |●                               ← 平稳区
   0 └─────┴─────┴─────┴─────┴──────→ 线程数
```

**拐点判断标准：**
1. 吞吐量不再随 VU 线性增长
2. 响应时间明显增大（超过基准的 2-3 倍）
3. 错误率开始上升
4. CPU/内存/连接数等资源达到瓶颈

## 4. 容量估算

### 4.1 基本公式

```
所需资源数 = 预期峰值QPS ÷ 单实例最大QPS × 安全系数

安全系数建议：
- 非核心业务：1.2
- 核心业务：1.5
- 金融/支付：2.0
```

### 4.2 实战：电商容量估算

**已知条件：**
- 历史峰值 QPS：500
- 预期增长：30%
- 单实例最大 QPS（从拐点测试得出）：150

**计算：**

```
目标峰值 QPS = 500 × 1.3 = 650
所需实例数 = 650 ÷ 150 × 1.5 (安全系数) = 6.5
向上取整 → 7 个实例
```

### 4.3 数据库连接池估算

```
连接数 = 实例数 × 每实例连接数
       = 7 × 20 = 140

数据库最大连接数应 > 140 (建议 200)
```

### 4.4 带宽估算

```
带宽(Mbps) = 吞吐量(QPS) × 平均响应大小(KB) × 8 ÷ 1000

例如：200 QPS × 50KB × 8 ÷ 1000 = 80 Mbps
```

## 5. APDEX 指标应用

### 5.1 什么是 APDEX

Application Performance Index（应用性能指数），用 0-1 的分数衡量用户满意度。

### 5.2 APDEX 阈值

| 等级 | 分数范围 | 含义 |
|------|----------|------|
| **满意 (Satisfied)** | RT ≤ T | 用户体验良好 |
| **容忍 (Tolerating)** | T < RT ≤ 4T | 可以忍受 |
| **不满 (Frustrated)** | RT > 4T | 体验差 |

### 5.3 APDEX 计算公式

```
APDEX = (满意数 + 容忍数/2) / 总采样数
```

### 5.4 JMeter 配置

在 `user.properties` 中配置：

```properties
# APDEX 阈值（毫秒）
jmeter.reportgenerator.apdex_satisfied_threshold=500
jmeter.reportgenerator.apdex_tolerated_threshold=1500
```

**阈值建议：**

| 接口类型 | T (满意) | 4T (容忍边界) | 说明 |
|----------|----------|---------------|------|
| 首页/登录 | 1000ms | 4000ms | 用户有耐心 |
| 搜索 | 500ms | 2000ms | 期望较快 |
| API 接口 | 200ms | 800ms | 程序调用 |
| 支付 | 500ms | 2000ms | 关键路径 |

### 5.5 APDEX 解读

```
APDEX = 0.95  → 优秀：95%用户满意
APDEX = 0.85  → 良好：大部分用户满意
APDEX = 0.70  → 一般：需要优化
APDEX = 0.50  → 差：严重影响体验
APDEX < 0.50  → 不可接受
```

## 6. 对比测试（A/B 测试）

### 6.1 场景

对比两个版本（如代码优化前后、不同配置、不同中间件）的性能差异。

### 6.2 测试方案

```
测试A: 优化前版本
├── 相同测试计划
├── 相同环境
├── 相同数据
└── 10 VU → 50 VU → 100 VU → 200 VU

测试B: 优化后版本
├── 相同测试计划
├── 相同环境
├── 相同数据
└── 10 VU → 50 VU → 100 VU → 200 VU
```

### 6.3 对比脚本

```bash
#!/bin/bash
# A/B 对比测试

run_test() {
    local VERSION=$1
    local THREADS=$2
    
    jmeter -n \
        -t compare_test.jmx \
        -Jthreads=$THREADS \
        -Jduration=180 \
        -l "results/${VERSION}_${THREADS}vu.csv" \
        -e -o "reports/${VERSION}_${THREADS}vu"
    
    jq '{version: "'$VERSION'", threads: '$THREADS', 
         avgRT: .Total.meanResTime, p99RT: .Total.pct3ResTime, 
         throughput: .Total.throughput, errorRate: .Total.errorPct}' \
        "reports/${VERSION}_${THREADS}vu/statistics.json"
}

echo "threads,version,avgRT,p99RT,throughput,errorRate" > results/comparison.csv

for threads in 10 50 100 200; do
    run_test "before" $threads >> results/comparison.csv
    run_test "after" $threads >> results/comparison.csv
done

echo ""
echo "对比结果已保存至 results/comparison.csv"
```

### 6.4 对比维度

| 维度 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 最大 QPS | 300 | 420 | **+40%** ✅ |
| P99 RT @200VU | 3500ms | 1200ms | **-66%** ✅ |
| 错误率 @200VU | 2.5% | 0.3% | **-88%** ✅ |
| CPU 使用率 | 85% | 60% | **-25%** ✅ |

## 7. Dashboard 报告深度解读

### 7.1 关键图表解读

#### APDEX 面板

```
APDEX: 0.92 (T=500ms) → 优秀
如果 APDEX < 0.7，重点关注 P90/P95 指标
```

#### Requests Summary 面板

```
总请求数: 500,000
失败数: 1,250 (0.25%)
如果失败率 > 1%，需要排查错误原因
```

#### Response Time Percentiles

```
P50: 120ms  ← 一半请求在120ms内完成
P90: 350ms  ← 90%请求在350ms内
P95: 550ms  ← 95%请求在550ms内
P99: 1200ms ← 1%的慢请求需要注意
```

> **经验：** P99 >> P50 说明存在明显的长尾延迟，通常与 GC、锁竞争、网络抖动有关。

#### Response Times Over Time

观察趋势：
- **平稳线：** 系统稳定
- **上升线：** 性能退化（资源泄漏、数据积累）
- **波动线：** GC 或外部依赖不稳定

#### Transactions per Second

- **平台区：** 达到最大吞吐量
- **波动：** 系统不稳定

### 7.2 异常模式识别

| 模式 | 特征 | 可能原因 |
|------|------|----------|
| **锯齿形 TPS** | TPS 周期性上下 | GC 暂停 |
| **响应时间阶梯上升** | RT 逐步增大 | 内存泄漏/连接池耗尽 |
| **TPS 突降** | 某个时间点 TPS 骤降 | 外部依赖超时/数据库死锁 |
| **错误率爬升** | 错误率逐步增加 | 资源耗尽 |

## 9. 常见问题排查

### 9.1 基准测试数据不稳定

**原因：** 预热不充分、JIT 编译、缓存未命中。

**解决：** 增加预热时间（至少 5 分钟），多轮测试取中位数。

### 9.2 拐点不清晰

**原因：** 加压步长太大或太小。

**解决：** 先用粗粒度步长（50→100→200→500）找范围，再用细粒度步长（150→175→200→225）精确定位。

### 9.3 APDEX 阈值设置不当

**解决：** 基于生产监控数据（如 APM 工具）设置真实 SLA 阈值，而非凭感觉。

### 9.4 对比测试结果不可信

**排查：**
1. 确保两次测试在相同时间段（排除外部因素）
2. 确保数据库数据量相同
3. 确保预热时间一致
4. 多轮测试取平均值
