# 03 - 认证与授权场景

> **难度：★★★☆☆** | **适用版本：JMeter 5.6.3** | **预计阅读：25分钟**

---

## 1. 场景概述

现代 API 几乎都需要认证。本章覆盖 5 种常见认证方式，每种都提供完整的 JMeter 配置方案。

**你将学到：**
- Basic Authentication 配置
- Bearer Token 认证（先登录获取 Token，再携带 Token 请求）
- OAuth 2.0 客户端凭证模式
- Cookie/Session 认证
- CSRF Token 处理
- API Key 方式

---

## 2. 方式一：HTTP Basic Authentication

### 2.1 场景

最简单的认证方式，将用户名密码通过 `Authorization: Basic base64(username:password)` 头发送。

### 2.2 配置 HTTP Authorization Manager

右键 Thread Group → Add → Config Element → **HTTP Authorization Manager**

| 参数 | 值 |
|------|-----|
| Base URL | `https://api.example.com` |
| Username | `${username}` |
| Password | `${password}` |
| Domain | （留空） |
| Realm | （留空） |
| Mechanism | `BASIC_DIGEST` |

> **注意：** Mechanism 选 `BASIC_DIGEST` 会自动选择服务器支持的认证方式。也可手动指定 `BASIC` 或 `DIGEST`。

### 2.3 作用域规则

- 放在 **Thread Group 级别**：该线程组下所有采样器自动携带认证头
- 放在 **单个采样器级别**：仅该采样器携带认证头
- Base URL 为空时，对所有请求生效

### 2.4 手动实现（不推荐）

也可以在 HTTP Header Manager 中手动设置：

| Name | Value |
|------|-------|
| `Authorization` | `Basic ${__base64Encode(${username}:${password})}` |

> 推荐使用 HTTP Authorization Manager，因为会自动处理 401 重试和 Digest 挑战。

## 3. 方式二：Bearer Token 认证（最常用）

### 3.1 场景

REST API 最常见的认证方式：
1. 先调用 `/api/login` 获取 Token
2. 后续请求在 Header 中携带 `Authorization: Bearer <token>`

### 3.2 测试计划结构

```
Test Plan: Bearer Token 认证
├── HTTP Request Defaults
│   └── Server: api.example.com
├── HTTP Header Manager (Content-Type)
│   └── Content-Type: application/json
├── setUp Thread Group
│   └── POST - 登录获取Token
│       ├── Body: {"username":"admin","password":"admin123"}
│       └── JSON Extractor → authToken = $.token
├── Thread Group (业务请求)
│   ├── HTTP Header Manager (Bearer Token)
│   │   └── Authorization: Bearer ${authToken}
│   ├── GET - 获取用户信息
│   ├── POST - 创建订单
│   └── ...
└── tearDown Thread Group
    └── POST - 登出
```

### 3.3 步骤详解

#### 步骤 1：登录并提取 Token

在 **setUp Thread Group** 中添加：

**HTTP Request - 登录：**

| 参数 | 值 |
|------|-----|
| Method | `POST` |
| Path | `/api/auth/login` |
| Body Data | `{"username":"${username}","password":"${password}"}` |

**JSON Extractor**（子元素）：

| 参数 | 值 |
|------|-----|
| Names of created variables | `authToken` |
| JSON Path expressions | `$.data.token` |
| Default Values | `NO_TOKEN` |

#### 步骤 2：业务请求携带 Token

在 **Thread Group** 中添加 **HTTP Header Manager**：

| Name | Value |
|------|-------|
| `Authorization` | `Bearer ${authToken}` |

> 该 Header Manager 放在 Thread Group 级别，该组下所有采样器自动携带 Token。

### 3.4 Token 过期处理

**方案一：使用 setUp Thread Group 每次重新获取**

setUp Thread Group 在主测试前执行一次，适合 Token 有效期较长的场景。

**方案二：使用 If Controller 判断 Token 状态**

```
Thread Group
├── If Controller (条件: ${JMeterThread.last_sample_ok} == false)
│   └── POST - 重新登录获取Token
│       └── JSON Extractor → authToken
├── GET - 业务请求
└── ...
```

**方案三：使用 While Controller + 定期刷新**

```
Thread Group
├── Counter (loopCount)
├── While Controller (条件: ${__javaScript(${loopCount} < ${LOOP})})
│   ├── If Controller (条件: ${__jexl3(${loopCount} % 100 == 0)})
│   │   └── POST - 刷新Token
│   │       └── JSON Extractor → authToken
│   └── GET - 业务请求
```

## 4. 方式三：OAuth 2.0 客户端凭证模式

### 4.1 场景

服务端到服务端通信，使用 Client ID + Client Secret 换取 Access Token。

### 4.2 OAuth 2.0 流程

```
客户端                         认证服务器                      资源服务器
  |                               |                              |
  |-- POST /oauth/token --------->|                              |
  |   grant_type=client_credentials|                             |
  |   client_id + client_secret   |                              |
  |                               |                              |
  |<-- {access_token, expires} ---|                              |
  |                               |                              |
  |-- GET /api/users -------------|----------------------------->|
  |   Authorization: Bearer xxx   |                              |
  |                               |                              |
  |<-- 200 OK [{users}] ----------|-----------------------------<|
```

### 4.3 JMeter 配置

#### setUp Thread Group - 获取 Token

**HTTP Request：**

| 参数 | 值 |
|------|-----|
| Method | `POST` |
| Path | `/oauth/token` |
| Body Data | `grant_type=client_credentials&client_id=${CLIENT_ID}&client_secret=${CLIENT_SECRET}` |

**HTTP Header Manager：**

| Name | Value |
|------|-------|
| `Content-Type` | `application/x-www-form-urlencoded` |

**JSON Extractor：**

| 参数 | 值 |
|------|-----|
| Variable Names | `accessToken` |
| JSON Path | `$.access_token` |
| Default | `NO_TOKEN` |

**JSON Extractor - 提取过期时间（可选）：**

| 参数 | 值 |
|------|-----|
| Variable Names | `expiresIn` |
| JSON Path | `$.expires_in` |
| Default | `3600` |

#### Thread Group - 使用 Token

**HTTP Header Manager：**

| Name | Value |
|------|-------|
| `Authorization` | `Bearer ${accessToken}` |

### 4.4 自动刷新 Token

使用 JSR223 PreProcessor（Groovy）判断 Token 是否过期：

```groovy
import java.time.Instant

def tokenTime = vars.get("tokenFetchTime")
def expiresIn = vars.get("expiresIn") as int

if (tokenTime == null || 
    Instant.now().epochSecond - (tokenTime as long) > expiresIn - 60) {
    
    // Token 即将过期或不存在，标记需要刷新
    vars.put("needRefreshToken", "true")
}
```

配合 If Controller：

```
If Controller (条件: "${needRefreshToken}" == "true" || "${accessToken}" == "NO_TOKEN")
└── POST - 获取新Token
    └── JSR223 PostProcessor (记录获取时间)
        └── vars.put("tokenFetchTime", String.valueOf(Instant.now().epochSecond))
```

## 5. 方式四：Cookie/Session 认证

### 5.1 场景

传统 Web 应用使用 Session + Cookie 机制。

### 5.2 配置 HTTP Cookie Manager

右键 Thread Group → Add → Config Element → **HTTP Cookie Manager**

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| Policy | `standard` | Cookie 策略 |
| Clear cookies each iteration? | `✓` | 每次迭代清空 Cookie |

> **关键：** 只需添加 HTTP Cookie Manager，JMeter 会自动处理 Cookie 的接收和发送，**无需手动提取和设置 Cookie**。

### 5.3 登录流程

```
Thread Group
├── HTTP Cookie Manager (自动管理Cookie)
├── POST - 登录
│   ├── Path: /login
│   └── Parameters:
│       ├── username = ${username}
│       └── password = ${password}
├── GET - 访问需要登录的页面
│   └── Path: /dashboard
└── GET - 访问其他页面
    └── Path: /profile
```

> HTTP Cookie Manager 自动从登录响应中提取 `Set-Cookie` 头，并在后续请求中自动携带 `Cookie` 头。

### 5.4 手动 Cookie（特殊场景）

如果服务器通过 JSON 返回 Session ID：

```json
{
    "sessionId": "abc123def456"
}
```

在 HTTP Cookie Manager 中手动添加：

| Name | Value | Domain | Path |
|------|-------|--------|------|
| `JSESSIONID` | `${sessionId}` | `api.example.com` | `/` |

## 6. 方式五：CSRF Token 处理

### 6.1 场景

服务端要求每次 POST/PUT/DELETE 请求携带 CSRF Token，Token 通常从页面或 API 响应中获取。

### 6.2 提取 CSRF Token

#### 从 HTML 页面提取（CSS Selector Extractor）

| 参数 | 值 |
|------|-----|
| Implementation | `JODD` |
| CSS Selector Expression | `meta[name=_csrf]` |
| Attribute | `content` |
| Reference Name | `csrfToken` |
| Default Value | `NO_CSRF` |

#### 从 JSON 响应提取（JSON Extractor）

| 参数 | 值 |
|------|-----|
| JSON Path | `$.csrfToken` |
| Variable Names | `csrfToken` |

#### 从响应头提取（Regular Expression Extractor）

| 参数 | 值 |
|------|-----|
| Reference Name | `csrfToken` |
| Regular Expression | `X-CSRF-TOKEN: (.+?)` |
| Template | `$1$` |
| Field to check | `Response Headers` |

### 6.3 在请求中携带 CSRF Token

**方式一：HTTP Header Manager**

| Name | Value |
|------|-------|
| `X-CSRF-TOKEN` | `${csrfToken}` |

**方式二：请求参数**

| Name | Value |
|------|-------|
| `_csrf` | `${csrfToken}` |

### 6.4 CSRF 测试计划结构

```
Thread Group
├── HTTP Cookie Manager
├── GET - 获取页面/CSRF Token
│   ├── Path: /login
│   └── CSS Selector Extractor → csrfToken
├── POST - 登录（携带CSRF）
│   ├── Path: /login
│   └── Parameters:
│       ├── username = admin
│       ├── password = admin123
│       └── _csrf = ${csrfToken}
├── GET - 操作页面（重新获取CSRF）
│   └── CSS Selector Extractor → csrfToken (覆盖)
└── POST - 执行业务操作
    └── Parameters:
        └── _csrf = ${csrfToken}
```

> **重要：** 每次 GET 页面后重新提取 CSRF Token，因为服务器端可能每次都生成新的。

## 7. 方式六：API Key

### 7.1 场景

服务端要求在每个请求的 Header 或查询参数中携带 API Key。

### 7.2 配置

**HTTP Header Manager：**

| Name | Value |
|------|-------|
| `X-API-Key` | `${API_KEY}` |
| `X-App-Id` | `${APP_ID}` |

> API_KEY 可通过 User Defined Variables 或命令行 `-J` 传入。

## 8. 认证方式选择指南

| 认证方式 | 适用场景 | 复杂度 | 安全性 |
|----------|----------|--------|--------|
| **Basic Auth** | 内部系统、简单 API | ★☆☆☆☆ | ★★☆☆☆ |
| **Bearer Token** | REST API（最常见） | ★★☆☆☆ | ★★★★☆ |
| **OAuth 2.0** | 第三方授权、微服务 | ★★★★☆ | ★★★★★ |
| **Cookie/Session** | 传统 Web 应用 | ★☆☆☆☆ | ★★★☆☆ |
| **CSRF Token** | 配合 Cookie 使用 | ★★★☆☆ | ★★★★☆ |
| **API Key** | 开放平台、B2B | ★☆☆☆☆ | ★★★☆☆ |

## 9. 常见问题排查

### 9.1 401 Unauthorized

**排查步骤：**
1. 确认 Token/用户名密码正确
2. 检查 Authorization 头格式（`Bearer xxx` vs `Basic xxx`）
3. 使用 View Results Tree 查看实际发送的请求头
4. 检查 Token 是否过期

### 9.2 Token 变量为空

**排查步骤：**
1. 检查 JSON Extractor 的 JSONPath 是否正确
2. 确认登录请求成功（Response Code 200）
3. 使用 Debug Sampler 查看变量值
4. 检查 setUp Thread Group 是否先于业务 Thread Group 执行

### 9.3 Cookie 丢失

**解决：**
1. 确认 HTTP Cookie Manager 已添加
2. 检查 Cookie 的 Domain 和 Path 是否匹配
3. 确认未勾选 "Clear cookies each iteration"（如果需要跨迭代保持登录状态）

### 9.4 CSRF Token 不匹配

**解决：**
1. 确保在 POST 之前重新 GET 页面提取最新 Token
2. 检查提取器的表达式是否正确
3. 查看 View Results Tree 中实际提交的 Token 值
